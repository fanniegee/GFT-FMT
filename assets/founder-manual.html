1. Purpose and current status

The Founder Control Centre is intended to be the central administrative environment for the Guvaza Family Trust. It brings together Trust configuration, beneficiary administration, company and service wallets, school and funeral requests, Admin authority, approvals, notifications, reports and activity review.

Important distinction: this manual describes the uploaded Founder HTML as it currently exists and separates observed behaviour from the target design. A control appearing on screen does not prove it is securely implemented or connected to the database.

The page is a mixed-stage application. Some functions communicate with server endpoints, while several lists, balances, timers and actions still use browser localStorage or front-end-only logic. Treat it as a working prototype and inspection console, not yet the final authoritative Trust system.

2. Access and security

On page load, checkFounderSession() requests GET /api/admin/me with browser credentials. It accepts the session only when the returned Admin role is FOUNDER. If no valid Founder session exists, a server login screen appears. Login is sent to POST /api/admin/login; a non-Founder Admin is redirected to admin.html.

  • Founder authentication is intended to be server-controlled.
  • Legacy browser password and two-factor controls are disabled and are not authentication authorities.
  • Cookie credentials are used for the session requests.
  • Every sensitive API read/write still needs server-side authorisation. Hiding a button is not security.
Operating rule: use only the authorised Founder account. Never share passwords, session cookies, invitation tokens or private beneficiary documents.

4. Beneficiary Pool — how it currently works

The screen contains manual add fields for full name, ID number and phone; tabs for Approved and Pending Auto; a deletion log; and PDF export.

Approved list

  • The approved bens array loads from localStorage key guvaza_bens.
  • Beneficiary wallet values load from guvaza_ben_wallets.
  • Manual Add, edit and delete currently update browser storage rather than a verified central database record.
  • The approved list renders from that local array. The reviewed flow does not visibly merge server-approved registration records into it.
  • The same local wallet value is displayed in both Login Wallet and Personal Wallet positions in the current rendering.

Pending Auto list

  • Rendering the Beneficiary Pool requests GET /api/registrations with the authenticated session.
  • The page filters returned records to status PENDING.
  • The display includes applicant name, system ID and parent name.
  • Approve sends POST /api/registrations/:registration_id/approve, then reloads the list after success.
  • Reject is currently a notice that rejection is unavailable because the server has no rejection endpoint.
  • The separate approvePending(i) helper is only a render/reload stub, not the server approval action.
Do not treat the two lists as one complete registry. The current Approved list and server Pending list have different sources. Approval success alone does not prove that a beneficiary was added to the Founder approved list, assigned the correct wallet or made payout-eligible.

5. Proper Founder pending-registration review

The target Founder environment must make each application reviewable as a complete case, not merely as a name in a queue. The current pending panel is too limited for that purpose.

Information the review workspace should show

  • Registration reference and submission date/time.
  • Applicant identity and contact details, masking sensitive fields until the reviewer is authorised.
  • Family relationship details and claimed parent/grandparent lineage.
  • Submitted documents, upload status and secure preview/download controls.
  • Current status, review history and outstanding verification requirements.
  • Possible duplicate warnings, without automatically merging people.
  • Reviewer identity, review time, decision reason and permanent decision history.

Required decision actions

ApproveRecord approval on the server, preserve the application, create or link the authoritative beneficiary record and return a clear result.
Request informationKeep the case pending or move it to an information-required state; record what is missing and notify the applicant.
RejectRequire a reason, record who decided and when, preserve case history and provide an appropriate notification.
Refer for verificationAssign the case to an authorised reviewer without granting final approval unless permissions allow it.
A pending application must never become payout-eligible because a browser form wrote a localStorage entry. Eligibility must follow a server-side decision and be recorded in the authoritative database.

7. Other sections — important cautions

  • Site Settings: saveCustomConfig() sends PUT /api/admin/config/public with the configuration payload. The page describes live configuration as stored in PostgreSQL.
  • Company and service wallets: values are read from browser localStorage in the reviewed Founder file; they are not reconciled financial books.
  • Beneficiary 24-hour distribution: a browser timer divides the local pool across the locally loaded approved list, credits local wallets and clears the local pool. A manual button can force it. This is not a safe final financial mechanism.
  • School auto-approval: autoApprove defaults to true if no saved preference exists and a check runs every four seconds. Disable this default until a server-authorised payment workflow is established.
  • 8th-day sweep: the current action transfers local Funeral and School balances into the local FBP value. It is not a durable server scheduler.
  • 5-Man Approval: the visible logic counts five browser checkbox values and checks a Founder override condition. It does not prove five separate people authenticated and approved.
  • Admin authority: the interface has role templates, modules, permissions, tasks, scope and overrides. The page describes scope as descriptive and reserved for later server enforcement.
  • Audit and notifications: local logs and browser notifications are not substitutes for server audit events and reliable delivery integrations.

9. Intended fully structured Founder environment

When complete, the Founder Control Centre should be a secure command environment rather than a collection of disconnected forms.

One authoritative recordRegistrations, beneficiaries, decisions, wallet transactions and Admin accounts are read/written through authenticated server APIs.
Founder-first visibilityOne queue shows pending cases, age, completeness, flags, assignment and decision history.
Separate statusesSubmitted, pending review, information required, verified, approved, rejected, suspended and payout eligible are explicit states.
Safe decision controlsActions require confirmation, permission checks, server validation and audit records.
Financial integrityBalances are ledger-derived; transactions are idempotent, authorised and reconciled.
Admin accountabilityEach Admin has a role, modules, permissions, scope, tasks, expiry conditions and server-enforced limits.
Operational transparencyFigures show their source and last refresh; API errors are visible and not silently replaced with misleading zeros.
Recovery and continuityBackups, audit history, error handling and recovery procedures are documented and tested.

11. Safety and control rules

  1. Do not approve a case solely because its name appears in a list or a browser flag says it is verified.
  2. Do not delete an application or beneficiary to resolve a discrepancy. Preserve it and use a documented correction, merge or archival process.
  3. Do not distribute funds using localStorage balances, browser timers or front-end checkbox results.
  4. Do not expose identity documents or personal data to Admins who do not need them for assigned duties.
  5. Do not allow an Admin to grant themselves greater authority or bypass Founder-controlled deployment.
  6. Do not treat an interface message as proof of a database write. Confirm the server response and reload the authoritative record.
  7. Before changing code, inspect the relevant HTML, API route, database schema and every page that reads/writes the same data.
  8. Test safely, review the code diff and obtain explicit approval before committing, pushing or deploying.

12. Recommended work plan

  1. Map the registration path: inspect registration page, API, database tables, approval route and beneficiary-facing pages. Document without editing.
  2. Reconcile the two lists: determine how server-approved registrations should populate the Founder list and identify all localStorage readers/writers.
  3. Design the review workspace: agree on case details, statuses, verification requirements and Founder actions.
  4. Repair the server workflow: implement secure APIs and database transitions for review decisions.
  5. Connect the Founder interface: make pending and approved views use the same authoritative API with accurate loading, empty and error states.
  6. Validate test cases: new submission, incomplete application, duplicate candidate, approval, rejection, information request, retry, expired session and permission denial.
  7. Only then address wallet eligibility: do not connect payouts until approved-beneficiary and eligibility rules are explicit and verified.
Agreed immediate focus: Beneficiary Pool and the Founder pending-registration inspection environment. The first technical step is a read-only end-to-end trace, followed by a proposed repair plan for approval. This manual does not authorise code changes.
